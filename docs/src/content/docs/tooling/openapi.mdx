title: OpenAPI
description: Generate an OpenAPI 3.1 document from a handshake api.

`@jayalfredprufrock/handshake/openapi` turns an api into an [OpenAPI 3.1](https://spec.openapis.org/oas/v3.1.0) document — paths, parameters, request/response bodies, and every error — with no code generation or runtime cost on your client or server.

## Usage

```ts
import { generateOpenApi } from "@jayalfredprufrock/handshake/openapi";
import { api } from "./contract";

const spec = generateOpenApi(api, {
  info: { title: "My API", version: "1.0.0" },
  servers: [{ url: "https://api.example.com" }],
});

// write it to disk, serve it, or hand it to Scalar / Swagger UI
await Bun.write("openapi.json", JSON.stringify(spec, null, 2));
```

`generateOpenApi(api, options)` returns a plain `OpenAPIV3_1.Document` (typed via [`openapi-types`](https://www.npmjs.com/package/openapi-types)).

## Options

```ts
interface GenerateOpenApiOptions {
  info: OpenAPIV3_1.InfoObject; // required — `title` and `version` are mandatory
  servers?: OpenAPIV3_1.ServerObject[];
  security?: OpenAPIV3_1.SecurityRequirementObject[];
  tags?: OpenAPIV3_1.TagObject[]; // defaults to one tag per named group
}
```

Everything that isn't part of the api (title, version, servers, security) is supplied here.

## What gets generated

| Api                                                 | OpenAPI                                                                                          |
| --------------------------------------------------- | ------------------------------------------------------------------------------------------------ |
| `:param` path segments                              | `{param}` path templates                                                                         |
| api `basePath` + group `basePath` + endpoint `path` | the full path key                                                                                |
| `params` / `query` / `headers` schemas              | individual `parameters` (path params always `required`; query/header `required` from the schema) |
| `body` schema                                       | `requestBody` (`application/json`)                                                               |
| `response` + `responseCode` (default `200`)         | the success response                                                                             |
| `errors` map + framework errors                     | error responses (see below)                                                                      |
| `description`                                       | operation `description`                                                                          |
| endpoint name                                       | `operationId`                                                                                    |
| `meta` (minus `tags`)                               | `x-*` extensions                                                                                 |

Endpoints marked `internal: true` are omitted from the document.

### Schemas and `$ref`

TypeBox schemas are JSON Schema 2020-12, which OpenAPI 3.1 accepts directly. A schema that declares a TypeBox **`$id`** is hoisted into `components/schemas` and referenced with `$ref` (so shared types appear once); schemas without a `$id` are inlined.

```ts
const User = Type.Object({ id: Type.String(), name: Type.String() }, { $id: "User" });
// → components/schemas/User, referenced wherever User is used
```

### Request and response strictness

Request bodies, parameters, and responses are emitted with the same `additionalProperties` handling the server enforces at runtime (see [Validation](/handshake/core/validation/#undeclared-properties)), so a generated client can't produce a body the server will reject, and can't be told to expect properties the server strips. Requests are documented with their declared `additionalProperties` preserved; responses are always documented as `additionalProperties: false`, matching the override `parseResponse` applies.

One consequence for `$id` schemas: a node whose closed form **differs** between request and response — i.e. it declares an `additionalProperties` other than `false` — sheds its `$id` and is **inlined** rather than hoisted to `components/schemas`. Such a node is closed as a response but left as declared as a request, so a single shared component could not describe both, and which form got emitted would depend on conversion order. Schemas that close identically in both directions (the overwhelmingly common case, where nothing is declared) keep their `$id` and stay reusable via `$ref`.

### Errors

Errors are **api-wide** — the union of every group's declared errors plus any declared on the api itself — so every operation documents the full set: the framework `VALIDATION_ERROR` (400) and `UNKNOWN_ERROR` (500), plus every declared error. Each is emitted as a named envelope schema (`{ kind, code, status, message, details }`) in `components/schemas`, and grouped into a shared response per status under `components/responses`. When multiple codes share a status, the response body is a `oneOf` with a `code` discriminator:

```jsonc
// responses for a 400 that has both VALIDATION_ERROR and a declared RATE_LIMIT:
{
  "oneOf": [
    { "$ref": "#/components/schemas/VALIDATION_ERROR" },
    { "$ref": "#/components/schemas/RATE_LIMIT" },
  ],
  "discriminator": {
    "propertyName": "code",
    "mapping": {
      /* … */
    },
  },
}
```

### Tags

An api is a named record of [contract groups](/handshake/core/contracts/#composing-contracts-into-an-api) (from `createApi`), so each group name becomes a tag and every operation is tagged with the group it came from. If an operation has no group, an endpoint's `meta.tags` (a `string[]`) are used instead.

## Scope

This is intentionally lean for now: JSON request/response bodies, parameters, and the full error model. Security schemes, examples, multiple content types, and a per-operation transform hook are planned for a later pass.
