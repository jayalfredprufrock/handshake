title: Validation
description: How Handshake validates and coerces request and response data.

Handshake validates all incoming request data and outgoing responses using [TypeBox](https://github.com/sinclairzx81/typebox) schemas. Each part of the request — path params, query params, headers, and body — has its own validation pipeline tailored to its characteristics.

All errors share a single `{ kind: "HANDSHAKE", code, status, message, details }` envelope. A failed **request** validation returns a **400** `VALIDATION_ERROR`; a failed **response** validation is a server bug and returns a **500** `UNKNOWN_ERROR` (the reason is never sent to the client — inspect it via `onError`). See [error handling](/handshake/server/hono/#error-handling).

## Undeclared properties

Handshake is strict about properties your schemas don't declare, **recursively** — at every depth, not just the top level. TypeBox itself is permissive here (an object schema with no `additionalProperties` accepts extra keys), so this strictness comes from Handshake, not from TypeBox.

| Input        | Undeclared properties | Opt-out                       |
| ------------ | --------------------- | ----------------------------- |
| Body         | **rejected** (400)    | yes — `additionalProperties`  |
| Query        | **rejected** (400)    | yes — `additionalProperties`  |
| Path params  | **rejected** (400)    | yes — `additionalProperties`  |
| Headers      | ignored               | n/a — always open at the root |
| **Response** | **silently stripped** | **no — always enforced**      |

Requests honor an explicit `additionalProperties` because an open request schema is a deliberate choice by the author, and only widens what a client may send:

```ts
// Extra properties pass through untouched
body: Type.Object({ name: Type.String() }, { additionalProperties: true });

// Extra properties are allowed, but must be numbers
body: Type.Object({ name: Type.String() }, { additionalProperties: Type.Number() });
```

**Responses do not.** `additionalProperties` is always forced to `false` on the way out, overriding whatever the schema declares. An open response schema means the server sends the client properties it never declared — a data leak rather than a feature. Because responses are _stripped_ rather than rejected, this override can never break a caller.

Three notes that apply everywhere:

- Only object nodes (those declaring `properties`) are closed. `Type.Record` (which uses `patternProperties`) and `Type.Unknown`/`Type.Any` are left alone, and are the supported way to model a genuinely dynamic payload — in a request or a response.
- `Type.Intersect` members stay open at their own root. `additionalProperties` consults only its sibling `properties`, so closing each member independently would make the intersection unsatisfiable rather than strict. Objects nested inside the members are still closed.
- TypeBox mapped types such as `Type.Partial()` and `Type.Pick()` **drop** the `additionalProperties` option from their source schema. Re-declare it on the result if you need an opt-out preserved.

Headers are the one deliberate exception: a real request carries dozens of headers nobody declares (`accept`, `user-agent`, tracing and proxy headers), so closing the root would reject essentially every request. Only the headers you declare are validated; the rest are ignored.

## Path Parameters

Path parameters arrive from the framework as strings. The params pipeline applies three steps:

1. **Default** — applies any default values defined in the schema
2. **Convert** — coerces string values to the target type (e.g. `"42"` → `42` for `Type.Number()`)
3. **Assert** — validates the coerced values against the schema, throwing on failure

Supported coercions:

| Schema type      | Input     | Output            |
| ---------------- | --------- | ----------------- |
| `Type.Number()`  | `"42"`    | `42`              |
| `Type.Integer()` | `"7"`     | `7`               |
| `Type.Boolean()` | `"true"`  | `true`            |
| `Type.String()`  | `"hello"` | `"hello"` (no-op) |

If a value cannot be coerced (e.g. `"abc"` for `Type.Number()`), the server returns a **400** `VALIDATION_ERROR`.

## Query Parameters

Query parameters are also strings, but they have the added complexity of potentially being arrays (from repeated keys like `?tags=a&tags=b`).

The query pipeline first **normalizes** the raw values, then applies the same Default → Convert → Assert steps as params.

### Normalization

Frameworks like Hono provide query values as `Record<string, string[]>` — every value is always an array. Handshake normalizes these based on the schema:

- **Array schema** (`Type.Array(...)`) — the array of values is kept as-is
- **Scalar schema** — if the array has exactly one element, it's unwrapped to a single value. If it has multiple elements, a **400** error is returned

```ts
query: Type.Object({
  q: Type.String(), // scalar — ?q=hello → "hello"
  tags: Type.Array(Type.String()), // array — ?tags=a&tags=b → ["a", "b"]
});
```

A single value for an array parameter is automatically coerced into a one-element array:

```
?tags=solo → ["solo"]
```

### Coercion

After normalization, the same type coercion as path params is applied. This means numeric and boolean query params are coerced from strings:

```
?page=2&limit=10&active=true → { page: 2, limit: 10, active: true }
```

Array items are also coerced individually:

```
?ids=1&ids=2&ids=3 → { ids: [1, 2, 3] }
```

Invalid or missing required query params return a **400** `VALIDATION_ERROR`.

## Headers

Request headers run the same Default → Convert → Assert pipeline as path params (header values arrive as strings and are coerced). Alone among request inputs, the header schema is **non-strict** at the root — only the headers you declare are validated; the request's many other headers are ignored. See [Undeclared properties](#undeclared-properties) for why.

Header names must be declared in **lowercase** (the framework reads them lowercased):

```ts
headers: Type.Object({ "x-api-key": Type.String() });
```

A missing or invalid declared header returns a **400** `VALIDATION_ERROR`.

## Request Body

Request bodies are assumed to be JSON objects. The body pipeline is intentionally strict:

1. **Default** — applies any default values defined in the schema
2. **Assert** — validates the value, defaulting `additionalProperties` to `false`

There is no coercion step — values must already be the correct type (unlike params and query which arrive as strings). This strictness means:

- **Missing required properties** → 400 error
- **Extra properties not in the schema** → 400 error
- **Wrong types** → 400 error

All three produce a **400** `VALIDATION_ERROR`.

Optional properties (defined with `Type.Optional()`) are allowed to be absent.

Extra properties are rejected at every depth, and the schema may opt out — see [Undeclared properties](#undeclared-properties). For unions, the default (and any opt-out) applies **per variant**, so one variant can be open while another stays closed.

The generated OpenAPI document applies the same defaulting, so the published spec advertises exactly the strictness the server enforces — see [OpenAPI](/handshake/tooling/openapi/#request-and-response-strictness).

## Response Validation

Response validation ensures that handlers return data matching the contract. It runs a different pipeline than request validation:

1. **Clean** — strips any properties not defined in the schema (silently, without error), with `additionalProperties` forced to `false` at every depth
2. **Assert** — validates that all remaining properties match the expected types

This means:

- Extra properties in the handler's return value are **silently removed** before sending — including nested objects, array items, and union variants
- A declared `additionalProperties` is **overridden**, not honored. Without this, a schema declaring `true` would pass undeclared properties straight through to the client. Use `Type.Record`/`Type.Unknown` for genuinely dynamic payloads. See [Undeclared properties](#undeclared-properties).
- Wrong types or missing required properties are treated as a **server bug**: the client receives a **500** `UNKNOWN_ERROR` (the reason is never leaked), and `onError` can detect it via `ResponseValidationError` (to log or alert).

### Configuring Response Validation

`validateResponse` is enabled by default and governs **both** success and error response bodies. It can be set on a whole `buildRoutes` bundle or per handler:

```ts
// Disable for the whole group
const routes = buildRoutes(api, "users", handlers, { validateResponse: false });

// Disable for a specific handler (closure form)
const routes = buildRoutes(api, "users", (group) => {
  group.implement("listUsers", () => [...users.values()], { validateResponse: false });
});
```

Per-handler settings override the bundle setting.

### Why strip instead of reject?

Request bodies reject extra properties because the client is sending data — extra fields may indicate a bug or a version mismatch that should be surfaced. Responses strip extra properties because the handler may return domain objects with internal fields that shouldn't leak to the client. Stripping is the safer default.

## Error Response Shape

Every error response uses the same envelope — `{ kind: "HANDSHAKE", code, status, message, details }`. For a `VALIDATION_ERROR`, `details` is a **normalized array of issues** — `{ path?, keyword?, message }[]` — rather than TypeBox's internal format. `path` is the offending value's location in dot notation (omitted at the root); `keyword` is the failed validation keyword. Request validation failures (params, query, headers, body) return status **400** with:

```ts
{
  kind: "HANDSHAKE";
  code: "VALIDATION_ERROR";
  status: 400;
  message: "Validation failed";
  details: [
    { path: "address.street", keyword: "type", message: "must be string" },
    { keyword: "required", message: "must have required properties age" },
  ];
}
```

Response validation failures return status **500** with `code: "UNKNOWN_ERROR"` (message `"Unknown error"`) — the underlying `issues` are exposed to `onError` (via `ResponseValidationError`) for logging, but never sent to the client.
